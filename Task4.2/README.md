# Задание 4.2. Стратегия горизонтального масштабирования

Выбраны публичный API-контур как точка входа новой нагрузки и Расписание как подтверждённое узкое место ключевого пользовательского сценария. 1С не выбрана объектом горизонтального масштабирования: это legacy-система с пределом около 50 RPS, поэтому её защищают локальная проекция, load leveling и rate limiting из задания 4.1.

| ИТ-система | Реализация горизонтального масштабирования | Ограничение | Описание решения для него |
|---|---|---|---|
| **Публичный API-контур: External API Gateway/WAF + цифровая платформа пациентов (Mobile API/BFF)** | Запустить минимум по 3 stateless-реплики Gateway и BFF в разных зонах доступности за L7 load balancer. <br/><br/>Не хранить сессии в памяти экземпляра; JWT проверять локально по кешированному JWKS. <br/><br/>Настроить HPA независимо для Gateway и BFF по RPS, CPU и p95 latency, с заранее прогретым минимальным числом реплик для вечернего пика. <br/><br/>Быстрые GET обслуживать из read-моделей и распределённого кеша; длительные команды принимать с `202 Accepted` и передавать в событийную платформу | Горизонтальное добавление API-реплик увеличивает конкуренцию за общие stateful-зависимости: БД read-модели, хранилище идемпотентности и количество соединений. <br/><br/>В результате узкое место переносится из BFF в БД/кеш, а connection storm может исчерпать их лимиты | Хранить состояние операции и идемпотентности вне BFF в отказоустойчивом хранилище; чтения направлять на реплики, горячие справочники — в кластерный кеш. <br/><br/>Использовать PgBouncer/ограниченные connection pools, backpressure и отдельные лимиты concurrency. <br/><br/>Масштабировать BFF только в пределах проверенной ёмкости зависимостей, подтверждённой нагрузочным тестом |
| **Расписание (Java REST + PostgreSQL)** | Запустить несколько stateless Java-инстансов за load balancer и масштабировать их по RPS, CPU, p95 и числу занятых worker threads. <br/><br/>Поиск свободных слотов и расписания врачей направлять на PostgreSQL read replicas; команды резервирования — только на primary. <br/><br/>Разделить read/write-модели, публиковать изменения через transactional outbox и обновлять кеш/проекции событийно | Единственный writer PostgreSQL и конкурентное изменение одного слота не масштабируются простым добавлением Java-инстансов. <br/><br/>Реплики чтения могут отставать, поэтому пользователь способен увидеть уже занятый слот, а параллельные команды — попытаться забронировать его дважды | Выполнять резервирование одной короткой транзакцией на primary с уникальным ограничением на активный `slotId`, optimistic locking/version и идемпотентным ключом. <br/><br/>После конфликта возвращать бизнес-результат «слот занят», а не повторять запись вслепую. <br/><br/>Партиционировать данные по клинике/диапазону дат, использовать HA-primary и read replicas только для поиска; при исчерпании одного writer переходить к контролируемому шардингу по клинике |

## Эксплуатационные условия

- Цель «50 000 пользователей» сама по себе не определяет число реплик. Перед запуском фиксируются профиль RPS, доля поиска и бронирования, допустимый replication lag, размеры payload и SLO завершения асинхронных операций.
- Автомасштабирование проверяется ступенчатой и пиковой нагрузкой, включая холодный старт, отказ зоны, отставание реплики и деградацию БД.
- Для API-контура контролируются RPS на реплику, p95/p99, saturation пулов и доля `429/5xx`; для Расписания — lock wait time, конфликты резервирования, lag реплик, latency транзакций и заполнение connection pool.
- Масштабирование не отменяет admission control: при перегрузке система должна раньше вернуть управляемый `429/503` с `Retry-After`, чем допустить каскадный отказ и потерю записи.
