# Задание 4.2. Стратегия горизонтального масштабирования

Выбраны публичный API-контур и Расписание. **Публичный API-контур — целевая ИТ-система компании**, а не только сетевой прокси: в него входят управляемые компанией External API Gateway/WAF и цифровая платформа пациентов (Mobile API/BFF), которые реализуют публичный контракт, аутентификационный периметр, авторизацию, rate limiting, оркестрацию мобильных сценариев и SLO нового канала. Именно сюда непосредственно приходит новая нагрузка мобильного приложения, поэтому его ёмкость и масштабирование компания должна планировать как единое целевое решение.

Расписание выбрано второй системой как синхронная зависимость поиска и создания записи и подтверждённое узкое место ключевого сценария. CRM и LIS не выбраны: они не обслуживают мобильный API синхронно в критическом пути записи, а результаты анализов должны поступать в отдельную read-модель через событийный контур; масштабирование их legacy-реализаций не устранит предел API или writer Расписания. Уведомления также не выбраны: это асинхронный post-processing после фиксации бизнес-операции, для которого важнее отдельно наращивать consumers, управлять очередями и backpressure, чем включать его в расчёт синхронной ёмкости API. Это не означает, что CRM, LIS и уведомления не требуют модернизации, — только что они не являются двумя целевыми объектами данного задания. 1С не выбрана по той же причине: legacy-предел около 50 RPS защищается локальной проекцией, load leveling и rate limiting из задания 4.1.

| ИТ-система | Реализация горизонтального масштабирования | Ограничение | Описание решения для него |
|---|---|---|---|
| **Публичный API-контур: External API Gateway/WAF + цифровая платформа пациентов (Mobile API/BFF)** | Запустить минимум по 3 stateless-реплики Gateway и BFF в разных зонах доступности за L7 load balancer. <br/><br/>Не хранить сессии в памяти экземпляра; JWT проверять локально по кешированному JWKS. <br/><br/>Настроить HPA независимо для Gateway и BFF по RPS, CPU и p95 latency, с заранее прогретым минимальным числом реплик для вечернего пика. <br/><br/>Быстрые GET обслуживать из read-моделей и распределённого кеша; длительные команды принимать с `202 Accepted` и передавать в событийную платформу | Горизонтальное добавление API-реплик увеличивает конкуренцию за общие stateful-зависимости: БД read-модели, хранилище идемпотентности и количество соединений. <br/><br/>В результате узкое место переносится из BFF в БД/кеш, а connection storm может исчерпать их лимиты | Хранить состояние операции и идемпотентности вне BFF в отказоустойчивом хранилище; чтения направлять на реплики, горячие справочники — в кластерный кеш. <br/><br/>Использовать PgBouncer/ограниченные connection pools, backpressure и отдельные лимиты concurrency. <br/><br/>Масштабировать BFF только в пределах проверенной ёмкости зависимостей, подтверждённой нагрузочным тестом |
| **Расписание (Java REST + PostgreSQL)** | Запустить несколько stateless Java-инстансов за load balancer и масштабировать их по RPS, CPU, p95 и числу занятых worker threads. <br/><br/>Поиск свободных слотов и расписания врачей направлять на PostgreSQL read replicas; команды резервирования — только на primary. <br/><br/>Разделить read/write-модели, публиковать изменения через transactional outbox и обновлять кеш/проекции событийно | Единственный writer PostgreSQL и конкурентное изменение одного слота не масштабируются простым добавлением Java-инстансов. <br/><br/>Реплики чтения могут отставать, поэтому пользователь способен увидеть уже занятый слот, а параллельные команды — попытаться забронировать его дважды | Выполнять резервирование одной короткой транзакцией на primary с уникальным ограничением на активный `slotId`, optimistic locking/version и идемпотентным ключом. <br/><br/>После конфликта возвращать бизнес-результат «слот занят», а не повторять запись вслепую. <br/><br/>Партиционировать данные по клинике/диапазону дат, использовать HA-primary и read replicas только для поиска; при достижении измеримых критериев ниже переходить к контролируемому шардингу по клинике |

## Учебная capacity-модель

Ниже приведён **расчётный сценарий, а не результаты измерений production**. Все коэффициенты являются явными допущениями и должны быть заменены данными аналитики и нагрузочных тестов:

1. Под «50 000 peak users» принимаются 50 000 пользователей, активных в одном 10-минутном пиковом окне.
2. На пользователя предполагается 12 API-запросов за это окно: открытие приложения, поиск, просмотр слотов и статусов. Средняя нагрузка равна `50 000 × 12 / 600 = 1 000 RPS`.
3. Коэффициент кратковременной неравномерности принят равным 2. Поэтому целевая ёмкость API-контура — **2 000 RPS** при соблюдении SLO, а не утверждение о фактически наблюдаемом трафике.
4. До тестов предполагается безопасная ёмкость одной реплики Gateway **250 RPS**, одной реплики BFF **125 RPS** уже с 50-процентным запасом относительно условного тестового порога. Расчёт даёт 8 Gateway и 16 BFF; для равномерного размещения в трёх зонах и потери одной реплики задаётся target **9 Gateway и 18 BFF**, minimum по 3, HPA maximum соответственно 15 и 30. Эти числа — стартовая конфигурация для проверки, а не измеренная производительность.

Пул BFF ограничивается **10 соединениями на реплику**, то есть 18 target-реплик создают не более 180 клиентских соединений к PgBouncer. PgBouncer мультиплексирует их в плановый server pool: до **120 соединений к primary** и до **80 на каждую read replica**; ещё 20% лимита PostgreSQL резервируется для миграций, мониторинга и аварийных операций. HPA не увеличивает число реплик, если рассчитанный суммарный pool превысит проверенный бюджет БД: сначала требуется нагрузочный тест или изменение pool/server capacity.

Для поиска допускается replication lag **не более 2 секунд**. При lag > 2 секунд в течение 5 минут создаётся alert и такие данные помечаются как потенциально устаревшие; при lag > 5 секунд реплика исключается из балансировки, а критичное read-after-write выполняется с primary/сессионным маркером. Для резервирования read replica никогда не является источником истины.

Шардирование PostgreSQL по `clinicId` запускается не по числу пользователей само по себе, а если после оптимизации запросов, индексов, партиционирования и read replicas в течение 15 минут выполняется хотя бы один критерий: writer CPU > 70%; write TPS > 80% подтверждённой нагрузочным тестом ёмкости primary; p95 транзакции резервирования > 200 мс или lock wait p95 > 50 мс; connection pool > 80%; либо одна клиника создаёт > 30% write-нагрузки и нарушает SLO остальных. Решение принимается только после подтверждения тренда минимум на трёх пиковых окнах, поскольку шардинг увеличивает стоимость транзакций, отчётности и эксплуатации.

## Эксплуатационные условия

- Цель «50 000 пользователей» сама по себе не определяет число реплик: приведённая модель лишь переводит её в проверяемые допущения. Перед запуском фиксируются фактический профиль RPS, доля поиска и бронирования, размеры payload и SLO завершения асинхронных операций, после чего модель пересчитывается.
- Автомасштабирование проверяется ступенчатой и пиковой нагрузкой, включая холодный старт, отказ зоны, отставание реплики и деградацию БД.
- Для API-контура контролируются RPS на реплику, p95/p99, saturation пулов и доля `429/5xx`; для Расписания — lock wait time, конфликты резервирования, lag реплик, latency транзакций и заполнение connection pool.
- Масштабирование не отменяет admission control: при перегрузке система должна раньше вернуть управляемый `429/503` с `Retry-After`, чем допустить каскадный отказ и потерю записи.
